# Blueprint: resolve `UpdateConfig` starter-header contract drift

Date: 2026-04-25
Priority: Low

## Goal

Bring the starter-config header text and its tests back into agreement.

This is not a deep architecture issue, but it leaves the suite red and should be cleaned up once the higher-priority work is done.

## Evidence

The starter config generator currently emits:

- `# Generated automatically by \`gupkg\`.`

Code: `gupkg.py:3781-3784`

The tests currently expect:

- `# Generated by \`gupkg --action UpdateConfig\`.`

Code: `tests/test_gupkg_pure.py:243`, `tests/test_gupkg_pure.py:280`

That is a direct contract drift between implementation and test expectation.

## Decision to make

Choose one policy and apply it consistently.

### Option A: treat the exact header sentence as implementation detail

- Relax tests so they assert semantic facts instead of one exact sentence.
- Example assertions:
  - generated file contains a generated-header comment
  - generated file contains synchronized metadata fields
  - generated file contains documented example blocks

This option is better if the exact sentence is not part of the user-facing contract.

### Option B: treat the exact header sentence as contract

- Define one constant for the header text
- Use it in `create_starter_config()`
- Use the same constant or exact string in tests

This option is better if the team cares about stable output wording.

## Recommendation

Prefer **Option A** unless there is a real user-facing reason to freeze the exact sentence.

Why:

- the core behavior of `UpdateConfig` is the generated structure and owned metadata sync, not a single comment line
- exact-string tests become brittle for low-value wording changes
- the repo already has enough strong behavior checks around generated content

## Scope

Touch only:

- `gupkg.py:3754-3830` if Option B is chosen
- `tests/test_gupkg_pure.py:236-286`

Do not mix this with metadata bug fixes or simplification work.

## Success criteria

- tests and implementation agree
- the suite is no longer red because of starter-header wording alone
- no unrelated behavior changes are introduced

## Non-goals

- no starter-template redesign
- no config schema change
- no `UpdateConfig` behavior change beyond the wording/test contract
